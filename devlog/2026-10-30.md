# Day 12 · 30 Oct 2026 · Our checker broke its own rule on the first press, and Apple notarized the build anyway

**TL;DR:** ThruLine has one rule it never bends. If a file in the project changes while the tests run, the run proves nothing. Today ThruLine broke that rule itself. On a fresh Rust project the first `cargo test` writes a `Cargo.lock`, ThruLine sees a file appear mid run, and it voids its own result. One press, zero proofs, every time. Chasing that down showed something worse. A check ThruLine runs can write to your repo, and on a stale lockfile it can rewrite a file you committed. We fixed it the honest way, not the convenient way. Also today: the app showed "check running" when nothing was running, a 3.6 second stall turned out to be one endpoint walking 26 GB on every page load, our own release script refused our own build twice (correctly), and the app is now signed and notarized by Apple and opens clean from a downloaded copy.

## The rule

A check that ThruLine runs records the project's inputs twice: when the process starts and when it exits.

```rust
let inputs_at_finish = thruline_core::examined_inputs::record_id(
    &thruline_core::examined_inputs::observe_source(Path::new(&root), None),
);
let inputs_moved = inputs_at_finish != inputs_at_spawn;
```

If the two differ, the run is stored as `completed` with the reason `inputs changed`. It is never attached as a pass, because the result doesn't describe what's on disk anymore. That rule exists for agents. An agent that edits a file while its own tests are running doesn't get a green tick for the old file.

## The rule caught us

The tester walked the one path that matters most: a Rust project, set up checking, accept the line, press once, get **Proven**. Instead the Change sat at "check running" and nothing ran.

The root cause came back in two halves.

1. **The first run voids itself.** The tester's project, like a lot of real Rust projects, has no committed `Cargo.lock`. Cargo creates one on the first `cargo test`. It's 150 bytes, untracked, and it appears between `inputs_at_spawn` and `inputs_at_finish`. So the run is recorded as "ran, checked nothing (inputs changed)". The second press finds the lockfile already there and passes. A product whose whole promise is "one press, a real verdict" needed two presses on the most common Rust setup there is.
2. **"check running" when nothing was running.** An accepted line with no run returned `in_progress` from the UI's criterion state, and that state is drawn as "check running". Our own seven-case table says a check that never ran reads **Not checked**. A status that says something is happening when nothing is happening is the same kind of lie we built ThruLine to catch. It's a bug, and it's being fixed as one.

And the part that hurt: **the end-to-end test for this exact path was green the whole time.** `c90_check_it_again_chain` uses a stand-in `cargo` that prints a passing run and exits. A fake cargo never writes a lockfile, so the test could never see the problem. It wasn't wrong. It just wasn't real.

## The worse question underneath

Once the lockfile showed up, the founder asked the question that mattered. Can a check ThruLine runs **write to the user's repo at all**?

Yes. We read it from the code instead of guessing.

- The dependency fetch runs `cargo fetch --offline --manifest-path <project>/Cargo.toml` (`crates/core/src/cargo_fetch.rs`). That creates `Cargo.lock` if it's missing.
- The test run itself runs the accepted command (`cargo test`) with the project root as its working directory (`crates/cli/src/check.rs`). We don't add `--locked` unless your own command has it, so a **committed but stale** `Cargo.lock` gets rewritten.

That last one is the line we don't cross. A tool that checks your agent's work shouldn't quietly change a file you committed.

## Three options, and the one we took

| Option | One press proves? | Touches a committed file? | A stale lock reads as |
|---|---|---|---|
| Do nothing | no, two presses | yes, rewrites it | inputs changed |
| Ignore any lockfile change | yes | yes, rewrites it | a pass, on a lockfile you never committed |
| Always `--locked` | no lockfile means no check at all | no | probably **Contradicted** (see below) |
| **Both, narrowly (taken)** | **yes** | **never** | **Not checked, with the reason** |

The "probably Contradicted" in that table is the scary row. With `--locked` and a stale lock, cargo exits 101 with an `error:` line about the lock file. Nothing in ThruLine recognises that message, and our failure rule reads `error:` in the output as a failed run. So a project whose tests pass could have been labelled **Contradicted** because of a lockfile. That's a false accusation, which is the one thing this product can never do.

What we're shipping:

- **A Cargo.lock the run created, where none existed, is not an input change.** Exactly one file, `Cargo.lock` at the project root, only when it was absent at spawn and untracked at finish. Anything else changed during the run still voids it: any edit, any other new file, a change to an existing lockfile. The receipt says it in words: "Cargo.lock was created by this run (none committed)."
- **When a Cargo.lock is committed, the fetch and the test run get `--locked`.** ThruLine never rewrites it. If cargo refuses because the lock is stale, the line reads **Not checked**, with the reason that the project's Cargo.lock is out of date and ThruLine doesn't change your files.
- **The consent sheet says so before you press.** "Cargo may create Cargo.lock and a target/ folder in this project, the same as running cargo test yourself. ThruLine never changes a committed Cargo.lock."

The tests are written red first, and the founder added a condition we're glad he did. The stale-lock test runs **real cargo against a genuinely stale lockfile**: a committed `Cargo.lock`, then a dependency added to `Cargo.toml` that the lock doesn't have. No mocked error string. The reason wording follows the stderr cargo actually prints, not what we think it prints. Two of the tests exist only as guards. They fail if anyone ever widens the rule past that one file.

## Signed, notarized, and refused twice on the way

Today was the first time the app went through the real release path end to end: build, Developer ID signature, Apple notarization, stapling, then the check that matters most, opening a copy marked as downloaded from the internet.

```
The validate action worked!
ThruLine_0.3.0_aarch64.dmg: accepted
source=Notarized Developer ID
/Volumes/ThruLine/ThruLine.app: accepted
source=Notarized Developer ID
```

Getting there took two refusals, both from our own release script, and both correct.

1. **The first build disagreed with itself.** In a fresh home with no licence, the binary said *"Free. Approving a version and checking a shown failure again need a Pro licence."* The release script on that same tree expected *"Free. Approving a version needs a Pro licence."* The script refused to ship a build whose words don't match its own record of what they should be. We moved to a newer tree.
2. **The CLI half refused again on the newer tree.** This time the binary was right and the script was stale. It still pinned a sentence that was never signed off. The script follows the binary now. The real finding was that our full release gate never ran this check, so a gate could go green on a build the release script would refuse. Now the gate runs it.

One small thing we fixed while we were there. The refusal message printed every field it compared except the sentence that actually differed, so it read like nothing was wrong. It prints the sentence now.

## 3.6 seconds we blamed on rendering for a week

The app has shown "Reading the record…" for a few seconds on first open for about a week, and we kept treating it as a render problem. It wasn't. `GET /api/storage`, the route that tells you how much ThruLine keeps on disk, walks the whole record folder on every request, and the Inbox waited for it before drawing anything. On a 26 GB real-world record that's 3.6 seconds of a blank screen.

The fix is two halves. The Inbox never waits for the size (it shows "Measuring…" until the number arrives), and the server works out the size on a background thread, caches it, and refreshes it after writes.

## 219 files our own tests left behind

Our release gate counts the temp entries every test binary leaves behind, and that count is not waived. Today we hunted them down one binary at a time under an empty `TMPDIR`: 202 in the app's test binaries, 17 in the core ones.

| Where | Left behind | Cause | Now |
|---|---|---|---|
| app hardening tests | 129 | each test made its own folder and never removed it | 0 |
| download tests | 23 | a read-only scratch tree `TempDir` couldn't delete | 0 |
| recorder route tests | 14 + 1 | mirror generations are sealed `0o500`, so `TempDir` couldn't remove them | 0 |
| licence tests | 1 | a scratch file for hashing; now hashed from stdin | 0 |
| CLI unit tests | 1 (a 1.3 MB `ledger.db`) | see below | 0 |
| a run-capture test | 1 | node's compile cache | open |
| e2e script, sidecar, ports | 23 + 22 + 4 | being fixed | open |

The CLI one was the best bug of the day. Six tests leaked one file between them, and no half of the six leaked on its own. A pair bisect found it: one test pressed **Run** and returned without waiting, so the check was still writing its ledger when the temp folder was deleted around it. It only showed up when another particular test ran right beside it. The fix is three lines, the same `wait_idle` its neighbours already had. The full binary is 632 passed, 0 left behind.

## Smaller things worth writing down

- **The test harness was leaking servers too.** Our QA lane had up to 14 `thruline ui` servers alive at once, each holding a multi-gigabyte test ledger open. That's a good candidate for the "machine load" behind a flaky check we chased last week. Every server now writes a PID file and gets killed when its walk ends, and nothing goes to a gate until the count is zero.
- **Backup before upgrade, at real size.** Upgrading a record now makes a verified copy first (`VACUUM INTO`, then rows, schema stamps and `quick_check`, then a rename). It's proven on fixtures. Next we're proving it on a 12.6 GB copy of a real record, and we'll post the times.
- **This release starts checks for Rust projects.** Python and Node checks work on their own branch, but the failing side isn't proven in the app yet. So this release says plainly what it can run, rather than running the wrong thing.
