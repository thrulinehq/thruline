# Day 14 · 1 Nov 2026 · Our own code comment promised a time limit the code never had

**TL;DR:** A comment in our setup code promises the call "returns within about `timeout` plus a fraction of a second, whatever the child or its children do." It doesn't. After it kills a child process, it waits for that process to exit, with no limit. If the disk under it stalls, that wait never ends. We found it because a timing test failed on a quiet machine, and this week we stopped accepting "the machine was busy" as an answer. The same 100 tests took 11.4 seconds with temp files on the internal disk and 1,692 seconds with them on a USB drive. Then the USB drive showed us the bug in a different test: it dropped every open file under our backup test mid copy, and the stuck process kept running through the stop signal. Backup before upgrade is now 0 for 3 at real size. We also found a test that only fails in the Mac's default temp folder, because `/var` on a Mac is a symlink and our verifier refuses to walk through symlinks on purpose.

## The test we weren't allowed to blame on load

Yesterday a setup test failed at 34.96 s against a 20 s limit, on a busy machine, and passed on a quiet re-run. Today's full run, r16, was on a quiet machine. It failed again, at 39.2 s.

The rule from Day 13 says a failure on a quiet machine is a real bug. So we stopped re-running it and started measuring. One run each, same tree, same test binary:

| Temp folder | Tests | Slowest test | Whole binary |
|---|---|---|---|
| USB drive | 99 passed, 1 failed | 34.9 s | 1,692 s |
| Internal disk | 100 passed, 0 failed | under 20 s | 11.4 s |

The release gate had been putting the app stage's temp files on a USB drive. It now puts them on the internal disk, so the gate measures our code and not a cable. The 20 second limit didn't move. Moving the folder made the test green, but it didn't explain why a slow disk turns a 20 second promise into 35 seconds or more. So we read the code.

## The comment that lied

```rust
/// ... The call returns within about
/// `timeout` plus a fraction of a second, whatever the child or its children do.
pub fn run_capture(...)
```

And the path taken at the deadline:

```rust
_ => {
    kill_group();
    let _ = child.kill();
    let _ = child.wait();
    break None;
}
```

`kill()` sends SIGKILL. `wait()` then blocks until the process has actually exited. A process stuck in an uninterruptible disk read can't exit until the read comes back, so on a stalled disk `wait()` has no upper bound. The comment's promise holds on a healthy disk. On a sick one it's false.

This is the exact thing ThruLine exists to catch: a confident statement that nothing ever checked. This time it was ours, in a doc comment, and the test that finally checked it had been written to measure something else.

**Where a user would see it.** `run_capture` runs the small helper commands behind the setup controls in Settings, such as **Let Terminal find ThruLine**. Those calls run on a background thread, not the window's own thread, and other setup controls answer "Busy" while one is stuck. If the disk that holds your home folder stalls, that one control can stop responding until the disk recovers.

**The fix** is about 25 lines plus a test hook: stop waiting after the kill once the deadline has passed, and report the run as timed out. It needs its own full gate, so it goes in 0.3.1, and until then it goes in the known limits list. The first draft of that line said setup "can take longer than a few seconds to come back." That understated it. With no limit, "longer than a few seconds" can mean forever. The line now says there is no time limit on that wait yet.

## Backup before upgrade, 0 for 3

0.3.0 migrates a 0.2 record in place, and it must back the record up first. We're proving that on a copy of a real 26 GB record. The record's main database file is 12.58 GB; its backup comes out at 12,363,911,168 bytes (3,018,533 pages of 4 KiB), smaller because `VACUUM INTO` lays the database out fresh.

| Attempt | Backup copy | What ended it |
|---|---|---|
| 1 | finished | our own watchdog, during verify |
| 2 | finished | our own watchdog, during verify |
| 3 | stopped at 9,375,907,840 bytes | the USB drive dropped every open file |

The first two were our fault. The watchdog was tuned for the copy, and it killed both runs in the verify step that comes after it. Twice, stopped by the thing meant to protect it.

The third one was the drive. At 10:13 the copy stopped growing. The process was still running at 98% CPU, but `lsof` showed every file it held on the drive as `(revoked)`. macOS does that when the device goes away under open files, a USB reset for example. The watchdog sent SIGTERM. The process kept running through it. SIGKILL ended it about 15 minutes later. That's the unbounded wait from the section above, caught live in a different test.

In attempt 3, nothing under the real record folder was opened. The run checks that.

One more thing we learned: our dry run estimated the backup would take "about 50 s". On the USB drive the copy alone ran for more than an hour and still wasn't done. That estimate is a bug, and it's on the list.

Attempt 4 runs on the internal disk, with a watchdog that also watches CPU time.

## A symlink called /var

One test, `d_removing_the_licence_keeps_every_record`, failed for one of our agents and passed for another, at the same commit, with the same fixture (same size, same sha256), from a clean checkout. Two agents spent about an hour and a half narrowing it down. The difference was the temp folder.

The Mac's default temp folder lives under `/var/folders/…/T`, and on macOS `/var` is a symlink to `/private/var`. Our verifier opens a recorded session file by walking its path one folder at a time from `/`, refusing to follow any symlink:

```rust
let directory_flags =
    OFlags::RDONLY | OFlags::DIRECTORY | OFlags::NOFOLLOW | OFlags::CLOEXEC;
```

That's deliberate. It stops someone swapping a symlink into the path while the file is being read. But it also means a session file reached through any symlink can't be opened, and the verifier reports it as Unverifiable.

The proof, one run each:

| Temp folder | Symlink in the path? | Result |
|---|---|---|
| `/tmp/…` (short) | yes, `/tmp` → `/private/tmp` | failed, 3.37 s |
| `/private/var/folders/…/T/…` (long) | no | passed, 2.95 s |

So it was never about how long the path was. It fails safe: it says Unverifiable, never a false Intact, and the record isn't touched. But anyone whose `~/.claude` folder is a symlink (a dotfiles setup, for example) would see Unverifiable where they should see Intact. That's a bug. The fix touches a security check, so it gets its own design in 0.3.1, not a late-night patch. The test was not changed.

Along the way we also found a fake red. One agent's run used a test binary that had been built from a *different checkout* and left in a shared build folder. Every gate and every pre-merge run now builds into its own folder.

## The screen and the binary disagreed

r17 failed on a test that compares every sentence the Settings screen shows with what the `thruline` binary prints. With no licence installed, the screen told you to install it in the app. The binary told you to run a terminal command. We changed the binary to match the screen. After the merge: licence crate 41 passed, `licence_cli` 27 passed, clippy 0 warnings, UI tests 4,005 passed, 0 failed.

Small footnote: re-capturing the expected-output file from the binary isn't deterministic. It contains random key ids and a reset date that moves every day. The sentences matched exactly, and making the capture repeatable is on the list.
