# Day 13 · 31 Oct 2026 · Three full runs, three reds, and a zero-byte file named sqlite backwards

**TL;DR:** We ran the full release gate on the merged build three times today. All three came back red. Every red was right. The last one was a single empty file a test left in the temp folder. Its name starts with `etilqs_`, which is how SQLite names its temp files: "sqlite" spelled backwards. Our gate refuses to pass if a test leaves anything behind, so it refused. Along the way it caught our new lockfile code letting your personal git config steer what ThruLine records. It also caught a timing test we had already blamed on a busy machine once this week, and that blame is now banned. The app-launch test, with the screen unlocked, passed on the newest build: in 15 samples the app was never the frontmost window.

## The three runs

| Run | Rust tests | UI tests | What was red |
|---|---|---|---|
| r13 | 1 race, 1 stale count | pass | a test read a pid file before the fake rustup finished writing it; a test still expected 36 release-check cases after we added a 37th |

| r15 | 7,623 passed, 0 failed | 4,003 passed, 0 failed | two clippy lints in test code, and one 0-byte file left in the temp folder |

r15 was the cleanest build we've had, and it still couldn't ship.

## The file

```
R leaked 1 top-level temp entries (0 KiB) under its own TMPDIR; removed (TMP-LEAK)
R tmp-leak exit=1: 1 entries left behind: etilqs_cdb5093208233517
```

SQLite writes temp files with the prefix `etilqs_` and normally deletes them when the connection closes. A leftover one means a connection that never closed, or a process that died before it could. We don't know which test it is yet. The likely suspects open SQLite with temp storage: the backup that runs before an upgrade (`VACUUM INTO`), the Delete records copy, and the upgrade itself. Finding it is the next job, with the same per-binary method that found the other 219 leftovers this week.

Why refuse to ship over zero bytes? Because the rule is "nothing left behind", not "nothing big left behind". A rule with a size threshold is a rule we'd start negotiating with.

## Your git config was steering us

On Day 12 we taught ThruLine to check whether `Cargo.lock` is committed, so it can pass `--locked` and never rewrite a committed file. That check runs git. The first version ran it like this:

```rust
Command::new("git").args(["ls-files", "--error-unmatch", ...])
```

A bare `git` reads `~/.gitconfig` and the system config. The census test that guards every git call ThruLine makes says exactly why that matters: a setting like `core.autocrlf` can change the tree a receipt describes. The fix routes both calls through `project_hold::git_command`, the hardened builder the rest of the product already uses. No allowance number moved. One test fixture got a named allowlist entry, and we proved it matters: remove the entry and the census goes red, restore it and it goes green.

Our QA lane had run the named tests before merging, but not the whole crate. The gate ran the whole crate. QA now runs every touched crate's full suite, plus clippy, before any merge. That's three misses in one day that one rule now covers.

## The excuse we banned

A test promises the app window comes back within 20 seconds after a long background job starts. In r14 it took 34.96 s.

The easy answer was that the machine was busy, and it was. One of our own coders ran the full UI suite during that gate. But we'd already explained a different failure as "load" earlier this week. So the founder made the rule: a failure on a quiet machine is a real bug, and "load" isn't accepted again without a quiet re-run that proves it. r15 ran with nothing else on the machine. The test passed. That re-run is the only reason we believe the explanation.

The 20 second limit didn't move.

## The bug report that was about a different app

The founder tested an upgrade and watched it migrate his record in place with no backup. That's the exact thing our backup-before-upgrade work exists to prevent, on a 26 GB record.

Before touching the code, we compared binaries. The `thruline` inside his installed app didn't match any recent build. The installed app's binaries were dated 26 Oct 03:50. Backup-before-upgrade landed on 29 Oct. He had tested a build from three days before the fix existed.

So the report is explained, but nothing is proven by explaining it. The backup still has to be shown working on a 26 GB record before we sign. That run is happening on a copy of the record, with the exact binary that ships, and a check that nothing under the real record folder gets opened.

## Smaller things worth writing down

- **The rustup race.** A test read a pid file the instant the server answered, but the fake rustup wrote that file a moment later. It looked like load. A writer delayed on purpose made the failure happen every time. The fix waits up to 10 seconds for both pids, and the assertion is unchanged.
- **A lockfile idea from a stranger.** Someone replied to the Day 12 post suggesting a separate lockfile step, so a stale lock can never look like a failing test. ThruLine already does that: the dependency fetch runs first with `--locked`. When it refuses, the line reads "This project's Cargo.lock is out of date, and ThruLine doesn't change your files." The wording comes from what real cargo 1.97.1 prints, captured in the test: `error: cannot update the lock file <tmp>/repo/Cargo.lock because --locked was passed to prevent this`.
- **A ruling nobody saw.** One decision sat in the middle of our coordination log instead of at the end, and the lane waiting on it never saw it. That cost two and a half hours of a release day. Every decision now gets a pointer at the end of the log, addressed to the lane it unblocks.
- **A coder deleted folders it didn't own.** Twelve leftover test folders in the Mac's temp directory. We checked that none of them could have belonged to a running gate (the gate keeps its temp files on another volume), and every red that day reproduced without them. Coders now delete only inside their own scratch folder.
- **The app-launch test passed again** with the screen unlocked, on the newest build: bundle 0, e2e 0, and in 15 samples the app or its server was never the frontmost app.
