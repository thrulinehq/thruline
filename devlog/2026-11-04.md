# Day 16 · 4 Nov 2026 · We signed the build at 3 a.m. Then it couldn't find cargo

**TL;DR:** On Monday night (2 Nov) we notarized 0.3.0 with Apple. Before that, our own release script refused our own binary, and the script was the stale one. The first person to install the signed app pressed the one button we sell, **Check it again**, and got "Tool not found: ThruLine couldn't find cargo." Cargo was on that Mac the whole time. The app looks for your tools with a login shell, and zsh only reads `~/.zshrc` when the shell is interactive. Thousands of green tests missed it because the test harness already had cargo on its `PATH`. The same test found two more problems in the signed build. One was a screen that said "Updating your record…" for 15 to 25 minutes after the update had finished in 179 seconds. The worse one: a true claim could read **Contradicted** because of a failure in some unrelated test. All three are fixed on r19, and the Rust suite is green at 7,630 passed, 0 failed. We sign again today.

## The release script that refused our binary

`release.sh` builds the binary, then asks it `licence status --json` in an empty home, before anything is signed. It refused:

```
refused: in a fresh home the release binary's paid surfaces are not exactly one,
approving a version, sold as Pro only
```

The guard was written when approving a version was the only paid feature. Since then we made a second one paid: ThruLine running a check itself from the app, with 5 free a month. The binary was right. The guard was out of date.

Our first fix would have broken it again. Our code has two lists: `PAID` (which plans unlock a feature, and it still holds the unsold Team plan) and `SOLD` (what anyone can buy, which is Pro only). The status JSON filters by `SOLD`. A guard that asserted `[pro, team]` would have refused a correct binary. So we read the real file the refused run left behind, instead of the code:

```json
"paid": [
  {"surface": "approve_version",   "plans": ["pro"]},
  {"surface": "run_check_from_app", "plans": ["pro"]}
],
"run_check_from_app": {"allowed": true, "plan_unlimited": false,
                       "limit": 5, "used": 0, "remaining": 5}
```

The new guard pins exactly that. It requires exactly these two features in this order, with no third, and plans of exactly `[pro]` on each. The fresh-home allowance must read 5 of 5 left. Every refusal now names the field and the value it got. Its test cases fail **23 of 42** on the old guard and pass **42 of 42** on the new one. Then we ran the full release check, with the new guard, on the real binary the refused run had built. It returned 0, and every check line printed.

**Did that mean the full gate had to run again?** We argued it instead of assuming either way. "The UI bundle is byte-identical" proves nothing here, because that compares the web assets, not the binary or the release scripts. What matters is whether anything that builds the binary changed. Git can answer that exactly:

```
git diff --name-only 98d96dc65 c1a11f8f6
  crates/cli/tests/release_check_cases.rs
  release/macos/check-release-binary-cases.sh
  release/macos/lib.sh
git diff --quiet 98d96dc65 c1a11f8f6 -- . ':(exclude)release/' \
  ':(exclude)crates/cli/tests/release_check_cases.rs'      # exit 0
```

`release/` isn't a workspace member, and nothing does `include_str!` or `include_bytes!` from it. The source digest the CLI stamps into the binary covers `crates/core/src`, `crates/cli/src` and the root manifests, and not `tests/`. So the tree that builds the binary was unchanged, and the gate's results carried over. Re-running the full gate would have cost two hours and wouldn't have tested the changed code, because no gate step runs the release check on a real release build. That gap is how a stale guard got as far as signing night. It's on the 0.3.1 list.

## "Tool not found: cargo"

The signed app, opened from /Applications on a normal Rust setup:

> The last check here: Tool not found. ThruLine couldn't find cargo, the program this check needs, where it looked. Nothing was installed.

Two things it did right: the verdict stayed **Not checked**, and the free check wasn't counted (5 of 5 left). But the feature we sell couldn't run.

The cause, in the code that finds your tools:

```
env_clear()  →  PATH=/usr/bin:/bin  →  $SHELL -l -c 'printf %s "$PATH"'
```

A zsh that's a login shell but not interactive reads `.zshenv`, `.zprofile` and `.zlogin`. It never reads `.zshrc`. This Mac loads cargo in `~/.zshrc`. So the login shell's `PATH` had no `~/.cargo/bin`, even though the app's own process did.

You can check your own Mac in one line:

```
env -i HOME="$HOME" PATH=/usr/bin:/bin zsh -l -c 'printf "%s\n" "$PATH"' | tr ':' '\n' | grep cargo
```

If that prints nothing while `which cargo` works in your terminal, you've got the same setup, and 0.3.0 as signed on Monday couldn't have found your cargo.

**Why thousands of green tests missed it:** our real-cargo test ran inside a harness that already had cargo on its `PATH`. It never launched the app the way macOS launches it.

**The fix:** the app now searches the login shell's `PATH` first. Then it tries `$CARGO_HOME/bin` and `~/.cargo/bin`, and last the app's own `PATH`, with duplicates removed and the order kept. The trust rule that decides whether a found program may run is unchanged. We didn't switch to an interactive shell to read `.zshrc`. Under a server, an interactive shell can hang on a prompt, run plugin code, or wait for a terminal. That would trade one failure for a worse one.

**The proof** used a launch through macOS, not a test harness. The `PATH` was forced bare (`/usr/bin:/bin:/usr/sbin:/sbin`), and cargo was only in `~/.cargo/bin`:

| Build | Result |
|---|---|
| 0.3.0 as signed Monday | `tool_not_found` |
| r19 | `cargo test --locked`, exit 0, 1 passed, 3 s |

## A true claim that could read Contradicted

When an agent says the tests pass, ThruLine proposes a line you can accept and check. That line is always project-wide: "When the project's tests run, every test passes." In the outside test it was proposed for a much narrower claim, "the 42/42 pin belongs in the signed tree." On our repo, 36 CLI tests fail in the Mac's default temp folder (the `/var` symlink from Day 14). So accepting that line would have run the whole suite, failed, and shown a true claim as **Contradicted**.

A tool that calls your agent a liar because of someone else's bug is worse than no tool. The word turned out to be chosen on the screen side, not in the engine that judges claims. The run's outcome was already `not_proven`, and a client mapping (`failedBasisOf` → `statusOf`) turned it into Contradicted. So the fix didn't touch how ThruLine judges evidence.

Now a line that came from an agent's claim never reads Contradicted when a project-wide run fails. It reads **Not checked**, with "N of M tests failed." Contradicted stays for lines you wrote yourself. Still open, and stated in the known limits: test names aren't stored yet (only counts), and the CLI's `acceptance` output and the PR preview can still say Contradicted.

## A screen that said "Updating…" for 20 minutes

The in-app upgrade on a real 26 GB record was correct. All 19 steps ran, and it said "Done in 179.2 s". The row census matched in 90 of 91 tables; `sensor_events` was +5, written during the run. It kept a 12.4 GB backup first. But the screen stayed on "Updating your record…" for another 15 to 25 minutes. The upgrade route ran its follow-up work (an export, a cache warm-up, and a catch-up over the whole record) *before* it set the phase to Done. A sample showed the UI server at 99% CPU in `memcmp`, inside that follow-up, with the upgrade child long gone. The route's test had passed `Box::new(|| {})` as the follow-up, so it could never see this.

Now the phase reads Done as soon as the upgrade exits 0, and the follow-up runs after it. The new test uses a deliberately slow follow-up.

## Smaller things

- **The run sheet said one thing and did another.** Before you pressed Accept, and in the ⌘K row, "Command" showed the agent's own 823-character shell chain, while the button actually runs `cargo test --locked`. It now shows the command it runs, and a test ties the two together.
- **A gate died quietly and an agent said it was still running.** The r18d gate died at 16:08 with no result. For the next 35 minutes, the agent watching it reported "log still advancing." It was reading the end of the log, not the file's modification time. It caught its own mistake, said so, and restarted the gate detached. The rule now: check the file time, not the tail. That's ThruLine's whole thesis, showing up inside our own release process.
- **Our own launch recipe was wrong.** For the cargo proof we told the agent to point the app at a scratch folder with `THRULINE_HOME`. But the record's path comes from `HOME`. For about 12 seconds, a debug build may have opened the founder's real record. The agent spotted it and said so straight away. `thruline verify` afterwards: every chain intact.
- **`verify` scared its own founder.** On sessions still being written, it prints `INTEGRITY MISMATCH (chain intact)`, because the file on disk has grown since it was recorded (942 → 948 lines). The chain is fine. The wording isn't, and it's on the 0.3.1 list.
- **A test failed once and passed on re-run.** `hq_catch_up` failed in one full run and passed in the next. We didn't call it flaky. One of today's fixes changed when catch-up runs, so it's filed as "race suspected, not proven."
- **The app inside the disk image isn't stapled on its own.** The disk image is notarized and stapled. The first open of a downloaded copy needs an internet connection. That's in the known limits, and the fix to the signing order is in 0.3.1.
