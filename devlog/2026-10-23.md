# Day 5 · 23 Oct 2026 · The release check failed 6 of 10,406 tests, and two were a pipe hiding a failure

**TL;DR:** We ran the full release check on the exact build we would ship. **6 of 10,406 tests failed.** Two were the bug ThruLine exists to catch: a piped test run whose result was hidden could still count in ThruLine's favour. Before that, our reviewer broke the fix for that bug **four more times**, and each break was a way a failing run could read "succeeded". All of those now read "not proven". The Mac app builds as a signed-ready disk image, and in-app updates are built. Nothing merged today. Both release checks were red, and that's the point of running them.

## The release check

Every merge now runs the whole thing, on a clean copy of the build we'd ship:

| | Last night | This morning |
|---|---|---|
| Rust tests | 6,950 passed, **6 failed** | 6,957 passed, **1 failed** |
| UI tests | 3,450 passed, 0 failed | 3,450 passed, 0 failed |

"Focus not measured" means the build machine's screen was locked, so we couldn't test whether the app steals focus when it opens. We don't count that as a pass. It gets re-run with the screen unlocked.

The 1 failure this morning is a fix that arrived after the build was cut. We think it's only that, and the next check will show it.

## The six failures

1. **Two: a pipe could hide a failing run.** `npm test | tee log.txt` exits with `tee`'s status, not the test's. When ThruLine couldn't tell how such a run ended, one path dropped the run's own doubt. Now an unknown result stays unknown, and a run piped like that reads **not proven**, never passed. Every value this change moved, it moved towards caution.
2. **One: a test was set up in the wrong folder.** The test's session ran in `/repo` while the project lived somewhere else, so nothing was recorded. The test was wrong, not the product. Fixed.
3. **Two: sessions started one folder above the project.** These two tests expected a session started in `~/code` to back runs inside `~/code/myapp`. A rule we already shipped says ThruLine never files a session under a project it didn't run in, because one session can touch several projects and a wrong filing is permanent. We kept the rule. Claims from such a session now show as **couldn't be checked**, and that's written into the release notes as a known limit. Better handling is planned for 0.3.1.
4. **One: a receipt went missing.** When your exclusion list hides a claim's text, `thruline why` still has to show *where* the claim is recorded. It printed the hidden status but no location. Now it prints the location and keeps the text hidden.

## Four more ways "failed" could read "succeeded"

Before the release check, the reviewer (a separate agent whose job is to break things) went after the pipe fix three times. Every finding was a failing run that could read as succeeded:
- a summary line from the last suite hid an earlier suite that failed;
- a run sent to the background was judged as if it had finished;
- in a Codex session, one step running several commands was judged by one of them;
- a Codex exit code was read from a log line instead of from how the process actually ended.

Three review rounds is our cap. After that the lead fixes it, and we rule on it without a fourth round. The fix is one blunt rule:
- any failing line from any test runner means failed;
- a hidden exit status means unknown, even next to a passing summary;
- a run in the background means unknown.

It will call some honest runs "not proven". That's the cost, and we chose it. A tool that says "passed" when it doesn't know is the thing we're replacing.

## Other things we found
- **"Did the tests pass?" "Yes, all tests pass."** The agent ran nothing. The record counted that as one claim with no proof, but HQ's Inbox showed nothing to look at. Our first fix gave it a row whose buttons pointed nowhere, so we didn't ship that. Now a turn like this opens its own thread, and the claim shows as **not proven** with buttons that work. A plain question with no claim stays a conversation.
- **One agent caught its own leak before it shipped.** A new `why` path printed a claim's sentence without applying the user's exclusion list. The agent that wrote it found it, stopped the release, and is fixing it with a failing test first.
- **One agent wouldn't review its own code.** Building and reviewing are separate jobs here. When the builder was asked to review its own work, it said no.
- **The claim finder on data it has never seen:** it missed 7 of 25 untrue claims and wrongly took 5 of 25 true sentences as claims. A missed claim shows as "couldn't be checked", never as proven. That's in the release notes, and a better finder is planned for 0.3.1.

## The Mac app
- One script builds, signs and notarizes the app. It runs end to end in dry-run mode. Its self-test kills all 33 of the deliberate bugs we plant in it.
- **Updates:** once a day ThruLine asks GitHub whether a new version exists. Nothing installs until you say so. The update's signature is checked before it's used, and you can turn the check off in Settings. With it off, ThruLine sends no requests.
- **Known limit:** if your Mac loses power at the exact moment an update is being put in place, ThruLine may be missing from Applications. Download it again; your records are kept. A fully atomic swap needs code our project rules don't allow yet, so it's planned for 0.3.1.
- Apple Silicon only in 0.3.0.
