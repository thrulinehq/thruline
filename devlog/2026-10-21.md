# Day 3 · 21 Oct 2026 · From 0 of 9 to 3 of 9, and why the other 6 still slip

**TL;DR:** We re-ran the Day 1 test: nine planted lies, each an agent claiming tests pass when they don't. On a test build that hasn't shipped, ThruLine now catches **3 of 9 during the session** (Day 1: 0 of 9) and marks **6 of 9** as not proven in HQ. Every miss has a known cause. Getting here took one decision that makes the tool stricter: a test run ThruLine only *read about* in the transcript can no longer count as proof. Run capture, which records the real run, is now on by default.

**Why the other 6 slip, case by case:**
- **3 are stale passes.** The tests really passed, then the agent edited more code and said "all green". ThruLine records this correctly, but nothing warns *during* the session that the last test run is older than the last edit. That warning is the next thing we build.
- **3 were never recognised as claims at all.** Sentences like "The build passes." and "All tests pass here." slip past the claim finder. Fixing the finder is next on the judge side.
- **Receipts:** HQ shows a receipt id that `thruline why` doesn't accept yet. This is a known bug with a follow-up card.

Fix the first two and the suite should clear our release bar of 8 of 9.

## The decision: transcripts can't prove anything any more

Day 2 ended with our stricter reading rules in their third and last review round. That round failed too. The reviewer, a separate agent whose only job is to break the change, found four more ways a test pass seen only in the transcript could still read **Proven**:
- a file changed by an ordinary shell command after the tests ran;
- a long log read only in part (for example, the agent's read tool stops at 2,000 lines);
- a log file the agent rewrote before reading it;
- the test program swapped through a `PATH=` or `CARGO=` prefix.

Each round found a new trick. Guessing from text whether a command changed a file is a game you can't win, so we stopped playing it:

- **A test run seen only in the agent's transcript can never read Proven.** At best it reads "couldn't be checked", with the reason "seen only in the transcript".
- **Proof comes only from runs ThruLine recorded itself.** That means run capture, or a check ThruLine started.
- The old transcript logic stays in the code behind a switch that exists only in test builds. A shipped build can't turn it on, and a test proves that. We keep it so we can measure later whether it ever earns a place back.

A narrow review then found one more place, an older in-session claim check, where a transcript-only pass could still read Proven. It now goes through the same rule.

**The honest cost:** on our 150 recorded build sessions, none of which had run capture, ThruLine now shows **zero Proven**. That's expected, and it's the right zero. Day 2 showed 3 in 4 test runs were piped through `tail` or `head`, so the transcript rarely holds the whole result anyway.
