# Day 10 · 28 Oct 2026 · Our own tests planted fake keys, and the export handed them back

**TL;DR:** The release check went fully green for the first time this week. The same build could write a GitHub token, an AWS key id, a private key and a password into an export file in plain text. Nothing in the green check had ever exported a record with a secret in it. Our privacy tests had: they planted fake secrets on purpose, and **10 of the 12 failing export tests were real leaks**, not stale tests. We fixed it at the door where data leaves the server, and said no to a faster fix that would have drifted.

## Green, and still leaking

The full release check passed on the combined build at 05:06. Formatting, lints, every Rust and UI test, the app build, the installer, the end-to-end run, all green.

Five hours later, an agent reading the red export tests showed that the export from that same build hands back secrets.

| Where the planted secret came out raw | How |
|---|---|
| The "export everything" file | summaries of shell commands were written with no masking |
| The packet export, with nothing ticked | the "leave out" boxes remove content types, not secrets |
| Copy as Markdown | same renderer, no masking at all |
| Waiver notes on screen and in the decision file | approval notes were masked, waivers were not |
| `--password=VALUE` | the masker knew `--password VALUE`, not the `=` form |

The secrets were fake: a made-up `ghp_` token, an AWS key id, a private key body, an `export API_KEY=` line and a password. Our own census tests plant them on purpose. Those tests had been red since they were written, filed as "inherited reds" and waiting for an owner. Today we read every one: 10 were real leaks and 2 are deliberate placeholders.

A second agent rebuilt the bug from scratch on the shipping binary. It planted a fake token in a single shell command, ran the export, and found the token in the output file. A finding we can reproduce twice, separately, is one we act on.

**The lesson:** a green check only covers the paths it runs. Ours never exported a record with a secret in it, so it could not see this. Now it does: an end-to-end test plants a token, runs every export, and fails if the token comes back. It was written red first, and it failed for the right reason.

## The fast fix we said no to

The first fix that came back made all 16 UI export tests pass. It was a JavaScript copy of the masker the record already uses in Rust.

We turned it down. Two detectors drift. The copy already missed shapes the original catches: percent-encoded text, the private-key structure check, and some header formats. Passing tests and safe exports aren't the same thing.

**The fix we took:** every string in every document the local server sends to the app goes through the record's own Rust masker first. The browser never holds a raw secret, so the screen, the export, the clipboard and the CSV can't leak one. The stored record is untouched. A document with nothing to mask goes out byte for byte the same.

On the fix branch: the Rust export tests went from 10 real leaks to 0 (the 2 placeholders stay red on purpose), and the masking corpus passes 17 of 17. The full release check runs on it next. If it isn't proven by Thursday noon, export is hidden in this release and comes in the next one. Shipping half a redaction is not an option.

## "Check it again" ran the wrong tests on Python projects

On a Python project, "Check it again" offered and ran `cargo test`, Rust's test command. The consent sheet even named both. The check started from the app only knew Rust.

A Python project is now offered `pytest` and never `cargo test`, and the sheet names exactly the one command that will run. Node (`npm`, `pnpm`, `yarn` by lockfile) is in progress. If either isn't verified before the freeze, the app says plainly what this version can run instead of running the wrong thing.

## Five times an agent asked to change a test

Today an agent asked five times to change or delete a test so its work could pass. Every time it asked first, which is the rule.

| Asked | Answer |
|---|---|
| Relax the page-description length check, because my approved text was 131 characters and the check wants 140 to 160 | **No.** I rewrote my text to 147 |
| Add an exception to the plan-name census for one sentence | **No.** I reworded the sentence to a form the census already allows |
| Drop a census rule because some rows build their text from variables | **No.** We added a test that renders those rows and checks the real output |
| Update a README test that still expected the old free tier | **Yes.** The product changed by a decision, so the test follows |
| Change a test fixture to a free user who has used their 5 checks | **Yes**, plus a twin test that a free user with checks left is allowed |

Three of the five, the right answer was to change my own words and keep the guard. An agent will reliably try to turn red into green. Whether the red is the code being wrong or the test being stale is a judgment, and it needs a person who knows why the test exists.

## The disk filled up while we were fixing the leak

Just before 1 pm the Mac had 1.8 GB free out of 494. Several agents had built the whole app at once, each in its own temporary folder on the system disk, at 6 to 9 GB a build. Nobody's build was wrong. Together they ate about 100 GB in an afternoon.

**The fix:** every build goes to an external drive, one folder per working copy, and is deleted when its job reports. Builds stop below 15 GB free. We're back at 95 GB.

## A note from me

I've been awake for 16 hours reading Rust I didn't type.

ThruLine exists because agents say "done" and "tests pass" when it isn't true. So the tool that checks AI-written code can't be waved through on a green tick itself. I believe every line of it should have a human who read it and knows why it's there. Today showed why. The check was green and the export leaked. An agent politely asked to loosen a test five times. A build ran the wrong test command for a whole language.

None of that is the agents being bad. They were fast, honest when asked, and they found most of it themselves. But "fast and honest when asked" is exactly why someone has to ask.
