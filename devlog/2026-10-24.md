## The two honest loops

The rule is simple. ThruLine stops the agent only when the record contradicts the claim: a recorded failure, a narrowed or flaky run, or weakened tests. A failure stops counting once a later run of the same command on the same code passes.

The reviewer, a separate agent whose only job is to break things, found two everyday loops where that rule went wrong:

1. **Fix a compile error.** `cargo test` doesn't compile. The agent fixes it, and `cargo test` passes 18 of 18. ThruLine kept the compile failure standing, because it couldn't read a test count from it, and "a comparison you can't make leaves the failure standing".
2. **Re-run quieter.** `pytest` fails, the agent fixes the code, then runs `pytest -q`, and everything passes. ThruLine treated `-q` as a different command, so the pass didn't count.

Both would have blocked an honest agent at the end of its turn. The fix keeps the rule and makes the comparison possible:
- a compile error, or a pytest run interrupted during collection, now reads as **zero tests run**. That's what actually happened;
- a failure that ran zero tests yields only to a later pass that ran **at least one** test, so an empty run still can't clear a failure;
- flags that only change output (`-q`, `-v`, `--color`, …) are ignored, and only for runners ThruLine knows;
- flags that narrow the run (`-k`, a single file, a test name) still have to match exactly, so a narrowed pass still counts as narrowed.

## "No, they don't all pass"

On a live run, the agent answered honestly: "No, they don't all pass: `node --test` ran 18 tests, with 16 passing and 2 failing." ThruLine's claim finder read "pass:" as a completion word and raised it as an unbacked claim.

The fix reads the sentence clause by clause. A pass clause that is negated, or that reports a shortfall, is a failure report, not a claim. There's no "starts with No" shortcut, so "No problem, all tests pass." is still a claim.

On the planted set it **lost 0 of 44 lies**. It also now catches a true claim it used to miss: "Earlier 2 failed, now all 18 pass."

## Other things we found
- **A Dock icon flashed for a moment at launch.** The app is meant to start hidden. On one launch test, it briefly started as a normal app with a Dock icon. That's what you'd see on day one, so it got fixed, not disclosed. The launch test now passes three times in a row with no Dock icon, and a separate check makes sure a normal start still shows one.
- **The first run of a brand-new app is slow on macOS.** The app's bundled command-line tool sometimes took more than 10 seconds to answer the first time. We measured it: macOS checks a new binary once, which costs 0.6 to 2.6 seconds here and more on a loaded build machine. You install a notarized app once, so it doesn't affect you. The test now allows one slower retry after a timeout, and writes down that it happened.
- **The app was switching test recording on for only two tools.** It ran setup with a bare system PATH, so it found `make` and `python3` but not `cargo`, `npm` or `pytest`. Now it sets up a fixed list of supported test tools, whatever PATH says. Our first fix read the person's whole shell setup instead, and we threw it out, because that can hang or slow down on some machines.
- **If ThruLine can't read your exclusion list, it now hides the text** instead of showing it. It says so: "(withheld: ThruLine couldn't read this project's exclusions)".
- **The release script could have published without the command-line tool.** A packaging check accepted any `.tar.gz`, and the app's update file is one. It now asks for the command-line archive by name.
- **The release check threw out a fully green build over one leftover temp folder.** One test didn't clean up after itself. That's the rule, so it's fixed, and the next build went through clean.
- **Our own summary line was wrong.** A green run printed "5 failed". Those lines came from small test programs our tests run on purpose, not from real failures. We're fixing the summary so the release evidence says what actually happened.
