# Day 2 · 20 Oct 2026 · The pass was real. It just wasn't about the code anymore.

**TL;DR:** We split the "no proof" and "couldn't check" piles from Day 1 into their causes. Agents almost never claim a test run that didn't happen. The common failure is a stale pass: the tests passed, the agent edited more code, then said "all green" anyway. We also tightened how ThruLine reads test runs, and we measured what that costs: 3 in 4 test runs in our sessions are piped into `tail` or `head`. Reading the transcript alone can't settle those, so recording the run itself is now the main job.

## Why claims had no proof

Day 1 counted the verdicts; this is what sits behind them. These counts come from the DEV half only (171 check claims). The TEST half stays sealed until the final run.

**No proof (36 claims):**

| Cause | Count |
| --- | --- |
| Tests passed, then code was edited, then "tests pass" was said without a new run | 32 |
| Ran part of the suite, claimed all of it | 3 |
| No run at all | 1 |

**Couldn't be checked (51 claims):**

| Cause | Count |
| --- | --- |
| The run happened inside a sub-agent; the main session only saw its summary | 39 |
| Output cut or garbled beyond reading | 3 |
| An edit ThruLine couldn't see happened before the claim | 2 |
| An edit happened while the run was going | 1 |
| Other | 6 |

**What it means:** the stale pass is the problem worth solving. An honest-looking "all green" that was true twenty minutes and three edits ago. Outright invented runs were 1 in 171.

## Tightening how we read a test run

An adversarial reviewer (a separate agent whose only job is to break the change) attacked our rules for when a recorded test run counts as proof. Round 2 failed with four holes, each one a trick we hadn't listed:
- a pipe into `head`, `sed` or `awk` that drops failure lines;
- an old log file printed with `cat` as if it were fresh output;
- edits made through tools we didn't recognise;
- cargo's own `error: 1 target failed` line, which we weren't reading as a failure.

Banning tricks one by one loses that game. So round 3 flips the rule:
- A pass counts only when the command is a plain test command and we read its whole output.
- Any tool that isn't on a known read-only list counts as a possible edit.

Round 3 is in review now, and it's the last round we allow. If it fails, we stop and rethink.

**The cost, measured, not guessed:** in our own sessions, 1,997 of 2,084 executed test runs were piped, and 1,514 of them into `tail` or `head`. Under the strict rule, nearly every honest pass seen only in a transcript becomes "couldn't be checked". That's the right call for a tool that says "Proven", but it means transcripts alone aren't enough. ThruLine has to record the run itself, before the pipe. That's run capture, below.

## v0.3 today
- **Honest "no check" for Node projects (merged).** ThruLine used to propose `cargo test` for a Node project, a check it could never run. Now it proposes no check and says why in plain words. On the way, the merge gate caught a regression: the first version also stopped Python and Go users' test runs from counting toward approval (16 failing tests). We scoped the change to Node only, re-ran the full gate, and it landed green: 6,482 Rust tests and 3,446 UI tests, 0 failures.
- **Run capture on by default.** This records the real test command, its full output and its exit code, before any pipe. It passed review after three rounds. Its on-screen sentences are waiting for sign-off, and it merges after that.
- **A "not bloatware" release check.** Before v0.3 ships, we'll measure what install touches, what each agent turn costs, disk growth and how much there is to learn, on a clean account. We'll set budgets from those numbers and fail the release if it goes over.
- **One card failed review three times:** `why` accepting every id that other commands print. It stopped at our three-round limit and comes back as a smaller follow-up.
