# Day 11 · 29 Oct 2026 · Every branch was green. The merge of all of them failed 21 tests, and one line read a missing exit code as a pass

**TL;DR:** Today we merged everything into one release candidate and ran the full release check on it, three times. Every branch had passed on its own. Together they failed **21** Rust tests on the first run, **16** on the second and **14** on the third. Working through those failures turned up four real bugs. A failed run could be drawn as "Not checked". A shell result with no exit code was read as exit 0, which counts as a pass. Delete records could copy a folder ThruLine was still writing to. And a Change screen could say "The tests passed" above a step that failed.

## The merge order deadlock

For about 30 hours, nothing reached the main branch. Every piece of work sat on its own branch, each with its own green suite:

- the export masking, the free-tier counter, the Settings buttons and the request checks on one branch;
- the new verdict words and the layout work on two others;
- the Python/Node check runner on a fourth;
- the screen fixes on a fifth.

Each branch was waiting for another to land first. The UI branch needed the signed pricing words from the masking branch. The masking branch's test pins needed the UI branch's verdict words. The Python branch conflicted with both on the same screen file.

The fix was boring and it worked: **one release-candidate branch, every input merged into it, one `ui/dist` rebuild at the end, one full gate.** Conflicts in generated files (the built UI bundle, 80+ paths per merge) are no longer a reason to rebase. They resolve to one side and get rebuilt once. Only source conflicts go back to their owners.

| Full release check on the merged build | Rust tests failing | UI tests failing |
|---|---|---|
| rc1 | 21 (in 8 test binaries) | not counted separately |
| r8 | 16 (7,578 passed) | 6 (3,961 passed) |
| r9 | 14 (7,580 passed) | 4 (3,963 passed) |

Each of those test binaries passed on its own branch. **A green branch is not a green release.** Every PASS now has to cite output from the merged commit, not from a branch.

## "Not proven" meant two things, so a failure could look like nothing

The engine has a deliberate rule: a statement read only from an agent's transcript is never **Proven**, because ThruLine didn't capture the run itself. The engine applied the same caution the other way. A failure seen only in the transcript was "held": stored as `not_proven` with `held_from: contradicted`, and not counted against the claim.

The trouble was downstream. `not_proven` also meant "no run at all", and about 40 places in the UI each turned the verdict into a word in their own way. So "the agent's own test run failed" and "nothing ran" could both reach the screen as **Not checked**.

We didn't rename the engine's enum this close to a release. We fixed it at the display layer. There's now one `statusOf(verdict)` function, and every adapter that brings a verdict into the UI goes through it. It maps seven cases to five words:

| Case | Word |
|---|---|
| never ran | Not checked |
| running | Not checked, "check running" |
| passed, a captured run on this version | Proven |
| **failed** (failed exit, failing finding, failed re-check, held failure) | **Contradicted** |
| stale, the proof moved | Needs a re-check |
| couldn't run (tool missing, refused, no permission) | Not checked, with the reason |
| invalid or unclear (gap in recording, can't tell which run) | Not checked, with the reason |

One sub-case got its own line: a captured failure that can't be tied to one command reads **Needs a re-check**, never Not checked and never Proven.

The acceptance test is a cross-screen census. It renders every screen that shows a verdict with a fixture holding all seven cases. It asserts the word and the `data-status` attribute for each, and checks that case 4 never comes out as Not checked, Proven or Needs a re-check. It caught the Approve sheet on its first run: the sheet had no `not_proven` entry, so a failed check fell through to "Not checked".

## `else { Some(0) }`

This is the line that decided whether the agent's own `npm test` "passed":

```rust
exit_code = if interrupted { None }
            else if r.is_error { exit_code_in(output) }
            else { Some(0) }
```

A shell tool result without the error flag was read as **exit 0, whatever its output said**. Our fixture's `npm test` printed `# pass 1 / # fail 1`, came back without the flag, and was recorded as "finished with exit code 0".

It's tightened now:

- **A pass by exit status needs an exit code that was actually recorded or printed.** No recorded code reads as unverifiable, "the run's exit code was not recorded".
- **A bare run whose output says it failed is a failure** (`failed`, `error:`, a `# fail N` above zero). `0 failed` doesn't count as a failure. That rule exists because the change briefly marked a passing tally as failed, and the tests caught it.
- The tests were written red first: the failing-output case, the no-output case, and the passing-looking case whose label used to say "exit code 0".

The point is that the change can only move a verdict **down**. It never makes one more favourable.

## The headline that said the tests passed

The tester walked a project whose tests really fail. The statement row read **✕ Contradicted**. Step 3 read **1 failed, 1 passed**. The headline at the top of the same Change read **"Not checked · The tests passed on wt-…"**.

That's the worst sentence ThruLine could print, and three green suites never saw it, because each one checked a different part of the screen. The fix routes the headline through the same `statusOf`. The test fixtures are the tester's own failing project ledgers. **It is not fixed as I write this.** It's the first thing on tomorrow's list.

## Delete records, and a folder that changes under the copy

Settings › Privacy & storage has a **Delete records…** button. It copies your record folder to the Trash, verifies the copy, and only then removes the original, so nothing is ever deleted outright.

Its tests passed alone. In the full release check, with temporary files on another volume, `across_a_volume_it_copies_verifies_and_only_then_removes_the_original` failed in 2 of 3 runs. It only failed when the other 11 tests in the binary ran around it, and run alone it passed 4 of 4. The error was always `ENOENT` on a different path inside the record folder: present when the snapshot was taken, gone by the time the copy reached it.

The cause was real, not a test artefact. **The app's server keeps writing to the record while the delete copies it**: the catch-up reader and SQLite's side files. Stopping the server inside the test would have made the test pass and left the race for users. So the delete itself now quiesces before it copies: it pauses recording, takes the catch-up lock for the whole operation, and closes the server's own handles. If it can't get all three, it refuses with "ThruLine is still writing to your record. Try again in a moment." and touches nothing. The acceptance bar is five full runs in a row on the other volume.

## Backup before the record changes shape

v0.2.0 is a public CLI download, so there are real records on real machines in the old schema. `thruline upgrade` migrated them **in place**, with no copy. A 0.2 binary would then refuse the upgraded record.

Now the upgrade backs the record up before the first migration step:

1. `VACUUM INTO` a `.partial` file;
2. verify it: the same rows in every table, the schema stamps, `PRAGMA quick_check`;
3. rename it to `backups/ledger-before-<schema>-<utc>.db`.

If the copy fails, the migration doesn't start. Backups are never overwritten or deleted. The upgrade output now says it:

```
backup      copying your record before changing it ... done
saved to    …/backups/ledger-before-c4a93038ac02-…db (checked: same rows in every table)
            ThruLine never deletes it; to go back, put it over the ledger file.
counted     90 tables, 2 rows (schema_migrations apart)
...
rows before = rows after for every existing table · new tables 6, all empty
```

That change broke one old test, which expected the upgrade's first line to be "counting every table before the upgrade". We changed the expected text, but kept the assertion that matters: the count still has to come before migration step 1.

## Python: `pytest -q` vs `python -m pytest`

On a correct Python project, "Check it again" ran `pytest -q`, which failed collection with `ModuleNotFoundError: No module named 'pyly'`. `python3 -m pytest -q` passed. The difference: `-m` puts the project root on `sys.path`, and the bare `pytest` script doesn't. Our allow-list doesn't permit `python3`, so the fix keeps the command and runs it with the project root **prepended to `PYTHONPATH`**.

The passing side is verified through real clicks: flat layout **Proven** (exit 0), `src/` layout **Proven**, Node **Proven** with `npm test`. The failing side isn't verified yet. The first time, a "Set up checking" rule hid the button on a Change that already had a failed transcript run. So for now, the release build says plainly that ThruLine starts checks for Rust projects, and the Python/Node path stays on its own branch until a failing project reads **Contradicted** through the app.

## Smaller things worth writing down

- **An unexplained "accepted" record.** In the tester's scratch ledger, a Change was accepted and a check run one second later, and nobody had clicked it. The route already refused cross-site pages, but any local process sending its own `Origin` header could post. That route now requires the server's own origin, and every hit is logged with its origin and peer, so the next one can be traced. We still don't know who wrote the first one. It goes in the notes as unexplained, not as solved.
- **A false accusation we almost made louder.** A known case: a pull request that edits `.thruline/policy.yml` turns an honest, older receipt red. The new verdict words would have retitled that check "Receipt contradicted". It now says "Receipt needs a re-check: the repository's policy changed after this receipt was signed." Real contradictions keep "Receipt contradicted".
- **"NOT MEASURED" is a result.** The app's end-to-end test watches whether the app steals focus. The Mac's screen was locked for all 840 samples, so the test wrote `focus NOT MEASURED` and exited 4 rather than claiming a pass. It runs again with the screen unlocked.
- **Exports, confirmed on the merged build.** Every export path (packet HTML/Markdown/JSON, whole and redacted, PR copy, Copy for the agent, Whole-Story Markdown/HTML) reports **raw secrets found: 0** against the planted fake keys.
