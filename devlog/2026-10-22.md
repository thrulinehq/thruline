## The gate that almost accused honest people

The in-session warning (we call it part C) works like this:
- When the agent says tests, a build, lint or a typecheck pass and no up-to-date recorded run backs it, ThruLine says so in the session, once. It doesn't stop the agent for that.
- It stops the agent only when the record contradicts the claim: a recorded failure, a narrowed, bypassed or flaky run, or weakened tests.

Then the reviewer, a separate agent whose only job is to break things, tried it with the gate on by default. It found five honest sessions the gate would have **blocked**:
- tests failed, the agent fixed the code, tests passed;
- the same for a build;
- `eslint .` over the whole project;
- `pytest tests/` (running the tests folder was misread as running only part of the suite);
- a narrowed run first, then the full suite.

All five were the checker's fault, not the gate's. It looked at the first failing run instead of the latest one, and it treated a test folder as "narrowing". The fix:
- a failure counts only if no later run of the same command on the same code passed;
- a full run outranks a narrowed one;
- naming a test folder isn't narrowing.

All five honest sessions now pass. The controls still fail as they should: a flaky run on the same code, a full failure "fixed" only by a narrowed pass, and a build that fails on the final code.

A lie detector that accuses honest people is worse than none. This is the reason the gate isn't on yet.

## The incident: tests opened a real user ledger

A privacy fix made `thruline claims` apply the user's exclusion list. To find that list, the code looked in the user's home folder. Tests set only ThruLine's own data folder, not the home folder, so during a full test run they opened the **real** ledger on the build machine. It was opened read-only and nothing wrote to it, but our rule is that no test touches a real ledger at all.

How it was caught: the merge gate went red with 26 failures. The real ledger was on a newer schema, so the tests failed instead of quietly passing. The reviewing session traced it, and the merge stopped.

The fix, failing test first:
- the lookup now follows ThruLine's data folder;
- a ledger it can't read prints one plain line instead of empty output;
- a new census test fails if any test can reach a real home folder.

The gate also checks the real ledger's size and date before and after every run. Its size changed during the run, but that came from the build machine's own live hooks, not from the tests.

## Other things we learned
- **Build machine stalls.** Builds froze five times at the same step, with the CPU idle. Each time the stuck piece was the macOS process that security-checks newly built programs, waiting on the external build drive. A restart didn't help. Building on the internal disk did.
- **The census found a detector nobody had listed.** A tamper check for tests that lost assertions (`assertion_count_decreased`) wasn't on any list, so the gate would only have flagged it. It now blocks, under "weakened tests". The census fails if a new blocking check appears without being named in the words people read.
- **Build, lint and typecheck claims now follow the test rule.** No up-to-date recorded run means a flag in the session. A contradicting run means a block.
- **The agents now run without the founder in the middle.** Two Claude Code sessions, one building and one reviewing, settle questions with each other in a shared file. Wording that people read still gets signed before it ships. Releasing, publishing and keys stay with the founder.
